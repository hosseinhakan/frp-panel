## ۱. این پروژه چه می‌کند؟

دو رابط روی یک زیرساخت مشترک:

| ابزار | چیست | اجرا |
|---|---|---|
| `frp-manager` | CLI تعاملی (فایل `frp-setup.sh`) | `sudo frp-manager` |
| `frp-panel` | پنل وب، یک باینری Go با کل UI داخل خودش | سرویس systemd روی پورت `9000` |

هر دو **همان فایل‌ها** را می‌خوانند و می‌نویسند:

- `/root/frp/server/*.toml` — کانفیگ سرورهای frps
- `/root/frp/client/*.toml` — کانفیگ کلاینت‌های frpc
- `/root/frp/gre/*.env` — تعریف تانل‌های GRE
- یونیت‌های systemd: `frps@…`، `frpc@…`، `gre-tunnel@…`، `frp-panel`

یعنی اگر در CLI یک سرور بسازید، بلافاصله در پنل دیده می‌شود و برعکس. هیچ دیتابیس
جداگانه‌ای وجود ندارد که با فایل‌ها ناهماهنگ شود.

## ۲. تانل چیست؟

**تانل (تونل)** یک مسیر مجازی بین دو سرور است که بسته‌های یک شبکه را داخل بسته‌های
شبکه‌ی دیگر جا می‌دهد؛ به این کار **کپسوله‌سازی (encapsulation)** می‌گویند. نتیجه این است
که دو سرور، با اینکه اینترنت بین‌شان است، از نظر شبکه مثل دو همسایه‌ی مستقیم رفتار
می‌کنند و می‌توانند IP خصوصی به هم بدهند.

دو حالت کلی:

- **تانل معمولی (forward):** کاربر به سرور خارج وصل می‌شود و سرور خارج ترافیک را به سرویس
  داخل می‌فرستد. سرویس داخل باید از بیرون قابل دسترس باشد.
- **تانل معکوس (reverse):** اتصال FRP از سرور خارج به سمت ایران برقرار می‌شود و سرویس‌های
  محلی سرور خارج از طریق IP عمومی ایران در دسترس قرار می‌گیرند. سرور خارج لازم نیست هیچ
  پورتی روی اینترنت باز کند.

این پروژه از حالت دوم استفاده می‌کند: **سرور ایران = ورودی/پل (frps)** و
**سرور خارج = خروجی/بک‌اند (frpc)**.

```
کاربر ──► IP عمومی ایران:6000 ──► frps (ایران، 10.100.111.2) ──► GRE (gt11) ──► frpc (خارج، 10.100.111.1) ──► 127.0.0.1:6000 خارج
```

چرا این کار را می‌کنیم؟

- سرور خارج هیچ پورت عمومی باز نمی‌کند؛ نه پنل، نه پورت کنترل FRP.
- پورت کنترل FRP (`7025`) روی IP عمومی گوش نمی‌دهد؛ فقط روی IP خصوصی تانل ایران.
- کاربر فقط IP عمومی ایران را می‌بیند و به همان پورت فورواردشده وصل می‌شود.
- یک تانل می‌تواند ده‌ها سرویس را جلو ببرد (هر پورت یک قاعده).
- ترافیک FRP با TLS و توکن محافظت می‌شود.

> **نکته‌ی مهم:** خود GRE **رمزنگاری ندارد**. امنیت از لایه‌ی FRP می‌آید
> (`transport.tls.enable = true` + توکن + `useEncryption = true`). GRE فقط مسیر و
> آدرس‌دهی خصوصی می‌دهد.

## ۳. تانل در این پروژه چطور کار می‌کند؟

### سه لایه

| لایه | چیست | در این پروژه |
|---|---|---|
| ۱. اینترنت | دو IP عمومی | `IP ایران` ↔ `IP خارج` |
| ۲. تانل | GRE (پروتکل ۴۷) | اینترفیس `gt11`، شبکه‌ی `10.100.111.0/30`، MTU `1280` |
| ۳. FRP | کنترل + فوروارد | `frps` روی `10.100.111.2:7025` (ایران)، `frpc` روی خارج متصل به همان |
| ۴. سرویس | پورت‌های شما | `remotePort` روی IP عمومی ایران → `localIP:localPort` روی خارج |

آدرس‌دهی پیش‌فرض (قابل تغییر است):

```
سرور ایران: 10.100.111.2/30   (سمت frps — ورودی/پل)
سرور خارج:  10.100.111.1/30   (سمت frpc — خروجی/بک‌اند)
اینترفیس:   gt11
```

### مسیر یک بسته برای پورت ۶۰۰۰

1. کاربر به `IP-ایران:6000` وصل می‌شود.
2. `frps` روی سرور ایران بسته را می‌پذیرد (این پورت با `remotePort = 6000` تعریف شده).
3. `frps` بسته را از طریق تانل به `10.100.111.1` (یعنی `frpc`) می‌فرستد.
4. `frpc` بسته را به `127.0.0.1:6000` روی سرور خارج تحویل می‌دهد.
5. پاسخ دقیقاً از همان مسیر برمی‌گردد.

بسته‌های GRE به این شکل ساخته می‌شوند (این کار را helper `frp-gre` انجام می‌دهد). روی
سرور ایران:

```sh
ip tunnel add gt11 mode gre local <IP-عمومی-ایران> remote <IP-عمومی-خارج> ttl 255
ip addr add 10.100.111.2/30 dev gt11
ip link set gt11 mtu 1280 up
```

و روی سرور خارج آدرس‌ها و local/remote برعکس می‌شوند (`10.100.111.1/30`).

### چرا MTU = ۱۴۰۰ و MSS clamp؟

هر بسته‌ی GRE حدود ۲۴ بایت سرریز (هدر بیرونی + هدر GRE) دارد. اگر MTU روی ۱۵۰۰ بماند،
بسته‌های بزرگ در مسیر جا نمی‌شوند و بی‌صدا دور ریخته می‌شوند. نشانه‌ی کلاسیک این مشکل:

> `ping` کار می‌کند، اتصال SSH برقرار می‌شود، ولی صفحه‌ها نصفه باز می‌شوند یا دانلود
> قطع می‌شود.

دو راه‌حل با هم اعمال می‌شوند:

- **MTU = 1280** روی اینترفیس تانل (پیش‌فرض همین پروژه؛ MSS = `MTU − 80` = `1200`).
- **TCP MSS clamping**: در بسته‌های `SYN` مقدار MSS کم می‌شود تا هیچ‌کدام از دو طرف
  بسته‌ی بزرگ‌تر از ظرفیت مسیر نسازند. helper این قانون را در جهت‌های ورودی و خروجی
  روی `gt11` نصب می‌کند (حالت پیش‌فرض `clamp`؛ گزینه‌های `1360`، `1240`، `1200`، `1220`، `off` هم هست).

### conntrack bypass

GRE یک پروتکل بدون حالت است و نگه‌داشتن state برای آن فقط سربار می‌سازد. helper قواعد
`raw PREROUTING/OUTPUT` را برای پروتکل ۴۷ با `NOTRACK` اضافه می‌کند تا بسته‌های GRE از
conntrack عبور نکنند.

## ۴. پیش‌نیازها

- دو سرور با **IP عمومی** (Ubuntu 22.04/24.04 یا Debian 12)، دسترسی `root`.
- امکان عبور **پروتکل ۴۷ (GRE)** بین دو IP. بعضی مسیرها این پروتکل را می‌بندند؛
  اگر بسته شد، تانل GRE برقرار نمی‌شود (بخش [۱۵](#۱۵-پرسشهای-متداول) را ببینید).
- ماژول کرنل GRE:

```sh
lsmod | grep gre || modprobe ip_gre
```

- پورت‌هایی که می‌خواهید منتشر کنید (مثلاً `22`، `6000-6006`).
- (اختیاری) دامنه برای سرویس‌ها.

بررسی سریع اینکه مسیر GRE باز است: پس از ساخت تانل، `ping` روی IP خصوصی جواب می‌دهد.

## ۵. نصب

### ۵.۱. نصب پنل با یک دستور (روی مخزن عمومی)

```sh
curl -fsSL https://raw.githubusercontent.com/hosseinhakan/frp-panel/main/scripts/install.sh | bash
```

اسکریپت نصب: معماری را تشخیص می‌دهد، tarball انتشار را دانلود می‌کند، باینری را در
`/usr/local/bin/frp-panel` می‌گذارد، یونیت systemd را **از داخل خود باینری** می‌نویسد
(`frp-panel install-unit`) و سرویس را فعال می‌کند.

گزینه‌ها:

```sh
bash install.sh --port 9000 --bind 10.100.111.2 --version v1.0.0 --base <URL>
```

| فلگ | کار |
|---|---|
| `--port N` | پورت پنل (پیش‌فرض `9000`) |
| `--bind ADDR` | آدرس گوش‌دادن (پیش‌فرض `0.0.0.0` یعنی همه‌ی اینترفیس‌ها؛ برای فقط loopback از `127.0.0.1` و برای دسترسی از تانل، IP تانل را بدهید) |
| `--version vX.Y.Z` | نسخه‌ی مشخص (پیش‌فرض: آخرین انتشار) |
| `--base URL` | آدرس دیگر برای دانلود tarball (آینه) |

> **مخزن فعلاً خصوصی است.** دستور بالا فقط وقتی کار می‌کند که مخزن عمومی باشد. دو راه
> دارید: عمومی‌کردن مخزن (`gh repo edit hosseinhakan/frp-panel --visibility public`) یا
> نصب با توکن (بخش بعد).

### ۵.۲. نصب از مخزن خصوصی (با توکن)

**راه اول — با `gh` روی سرور:**

```sh
# روی سرور، بعد از gh auth login
curl -fsSL -H "Authorization: Bearer $(gh auth token)" \
  -o /tmp/frp-setup.sh \
  https://raw.githubusercontent.com/hosseinhakan/frp-panel/main/frp-setup.sh

gh release download v1.0.0 -R hosseinhakan/frp-panel \
  -p 'frp-panel_linux_amd64.tar.gz' -D /tmp

sudo bash /tmp/frp-setup.sh          # نصب CLI؛ از منو با گزینه ۹ خارج شوید
sudo frp-manager panel install --file /tmp/frp-panel_linux_amd64.tar.gz
```

**راه دوم — فقط با `curl` و یک Personal Access Token:**

```sh
export GH_TOKEN=ghp_xxxxxxxxxxxxxxxx
REPO=hosseinhakan/frp-panel
ASSET=frp-panel_linux_amd64.tar.gz     # روی arm64: frp-panel_linux_arm64.tar.gz

curl -fsSL -H "Authorization: Bearer $GH_TOKEN" -o /tmp/frp-setup.sh \
  "https://raw.githubusercontent.com/$REPO/main/frp-setup.sh"

url=$(curl -fsSL -H "Authorization: Bearer $GH_TOKEN" \
  "https://api.github.com/repos/$REPO/releases/tags/v1.0.0" \
  | jq -r --arg n "$ASSET" '.assets[] | select(.name == $n) | .url')

curl -fsSL -H "Authorization: Bearer $GH_TOKEN" \
  -H "Accept: application/octet-stream" "$url" -o "/tmp/$ASSET"

sudo bash /tmp/frp-setup.sh
sudo frp-manager panel install --file "/tmp/$ASSET"
```

> دانلود مستقیم از مسیر `releases/download/...` برای مخزن خصوصی توکن را قبول نمی‌کند؛
> باید از API (همان بالا) استفاده کنید.

### ۵.۳. نصب CLI

```sh
git clone https://github.com/hosseinhakan/frp-panel.git
cd frp-panel
sudo bash frp-setup.sh
```

اسکریپت خودش را در `/usr/local/bin/frp-manager` نصب می‌کند. بعد از آن:

```sh
sudo frp-manager          # منوی تعاملی
frp-manager version
```

### ۵.۴. اولین ورود به پنل

رمز عبور **یک‌بارمصرف** فقط در اولین اجرا ساخته و در journald چاپ می‌شود:

```sh
journalctl -u frp-panel --no-pager | grep -i password | head -n1
```

سپس آدرس پنل را باز کنید:

```sh
systemctl status frp-panel --no-pager     # وضعیت
curl -s http://127.0.0.1:9000/api/health  # تست سلامت
```

پنل به‌صورت پیش‌فرض روی `0.0.0.0` (همه‌ی اینترفیس‌ها) گوش می‌دهد و نصب‌کننده
در صورت وجود `ufw` پورت را خودکار باز می‌کند؛ پس مستقیماً باز کنید:

```sh
http://<IP-عمومی-سرور>:9000
```

اگر می‌خواهید پنل فقط از loopback در دسترس باشد:

```sh
bash install.sh --bind 127.0.0.1 --port 9000
ssh -L 9000:127.0.0.1:9000 root@<IP-سرور>
# بعد در مرورگر: http://127.0.0.1:9000
```

یا آن را روی IP تانل بایند کنید:

```sh
bash install.sh --bind 10.100.111.2 --port 9000
```

بعد از ورود، پنل شما را مجبور می‌کند رمز یک‌بارمصرف را به یک رمز واقعی تغییر دهید.

## ۶. ساخت تانل، قدم به قدم

نمونه‌ی کامل برای دو سرور:

```
سرور ایران : IP عمومی 1.2.3.4 ، IP تانل 10.100.111.2  (ورودی/پل، frps)
سرور خارج  : IP عمومی 5.6.7.8 ، IP تانل 10.100.111.1  (خروجی/بک‌اند، frpc)
```

### ۶.۱. سریع‌ترین راه — ویزارد یکپارچه (پیشنهادی)

دیگر لازم نیست GRE و FRP را جدا بسازید؛ منوی **۱۴** هر دو را با هم می‌سازد.

**روی سرور ایران:**

```sh
sudo frp-manager
# 14) FRP over GRE Reverse (Quick Setup) → 1) Iran node — entry / frps
```

IP عمومی ایران و IP عمومی خارج را وارد کنید. نام اینترفیس و پورت کنترل به‌صورت
خودکار با اولین مقدار آزاد پر می‌شوند (`gt11` / `7025` روی سرور تازه). ویزارد
تانل را با `10.100.<n>.2/30 ↔ 10.100.<n>.1/30`، MTU `1280`، `NOTRACK` پروتکل
۴۷ و TCPMSS clamp می‌سازد، یک توکن ۳۲ کاراکتری تولید می‌کند، `frps` را **فقط**
روی IP تانل بالا می‌آورد و در پایان **mirror payload** را چاپ می‌کند.

اگر `gt11` یا شبکه‌ی `/30` یا پورت `7025` قبلاً اشغال شده باشد، ویزارد خودش
مقدار آزاد بعدی (`gt12`، `10.100.112.0/30`، `7026`) را انتخاب می‌کند و در
خروجی هشدار می‌دهد؛ بنابراین یک سرور ایران می‌تواند چند تانل هم‌زمان به چند
سرور خارج داشته باشد.

**دستور یک‌مرحله‌ای برای سرور خارج (بدون نیاز به نصب پنل):** در همان خروجی
ویزارد، بخش **1-click Foreign setup** (یا دکمه‌ی **foreign** روی هر ردیف frps)
را باز کنید، IP عمومی خارج، پورت‌ها (پیش‌فرض `8989`) و در صورت نیاز Raw speed را
بدهید و روی **Generate command** بزنید. یک بلوک Bash آماده می‌گیرید که با یک
پیست روی سرور خارج (فقط با دسترسی root):

1. تانل GRE قرینه + سرویس systemd پایدار را می‌سازد؛
2. اگر `frpc` نصب نباشد آن را دانلود و نصب می‌کند؛
3. فایل `/root/frp/client/<name>.toml` را با همان IP تانل ایران، پورت کنترل،
   توکن و تنظیمات `transport.*` می‌نویسد؛
4. `gre-tunnel@` و `frpc@` را فعال/ری‌استارت کرده و با `ping` و
   `systemctl is-active` صحت اتصال را گزارش می‌دهد.

**روی سرور خارج (روش جایگزین با ویزارد/CLI):**

```sh
sudo frp-manager
# 14) FRP over GRE Reverse (Quick Setup) → 2) Foreign node — exit / frpc
```

payload را پیست کنید (یا فایل آن را بدهید)، پورت‌های محلی را به‌صورت لیست
کاما‌دار مثل `8989,8443,2053` و حالت TCP / TCP+UDP را وارد کنید. ویزارد تانل
قرینه (`10.100.<n>.1/30 ↔ 10.100.<n>.2/30`) و `frpc` می‌سازد، سپس IP تانل
ایران را از داخل تانل ping می‌کند و وضعیت `frpc` را نشان می‌دهد.

- حالت عادی: TLS و رمزنگاری per-proxy روشن است.
- **Raw speed:** تیک آن را بزنید تا `tls.enable=false`، `useEncryption=false`،
  compression و tcpMux خاموش شوند؛ مناسب VLESS/VMess/Hysteria که خودشان
  رمزنگاری شده‌اند.

اگر نام اینترفیس محلی اشغال باشد، فقط نام اینترفیس عوض می‌شود (شبکه‌ی `/30`
قرینه دست‌نخورده می‌ماند). واچ‌داگ دولایه (`frp-watchdog`) هم به‌صورت پیش‌فرض
فعال می‌شود (با تیک قابل غیرفعال‌کردن).

نسخه‌ی غیرتعاملی:

```sh
# روی ایران (خروجی شامل payload و دستور آماده است)
frp-manager reverse iran --iran-public 1.2.3.4 --foreign-public 5.6.7.8

# روی خارج
frp-manager reverse foreign --payload /root/mirror.env \
  --ports 8443,2053,443 --proto both
```

### ۶.۲. راه دستی — فقط GRE

**روی سرور ایران:**

```sh
sudo frp-manager gre create \
  --local-public 1.2.3.4 \
  --remote-public 5.6.7.8 \
  --iface gt11 \
  --local-private 10.100.111.2/30 \
  --remote-private 10.100.111.1/30 \
  --mtu 1280 \
  --mss 1200
```

یا از منوی تعاملی: `frp-manager` → گزینه **۱۰) GRE Tunnel Manager** → **۲) Create tunnel**.

**روی سرور خارج** همان دستور با جای عوض‌شده:

```sh
sudo frp-manager gre create \
  --local-public 5.6.7.8 \
  --remote-public 1.2.3.4 \
  --local-private 10.100.111.1/30 \
  --remote-private 10.100.111.2/30
```

یا از خروجی «mirror» استفاده کنید. اگر طرف مقابل هنوز پیکربندی نشده باشد، دستور سازنده
خودش دستور آماده‌ی نود دیگر را چاپ می‌کند. بعداً هم می‌توانید بگیرید:

```sh
frp-manager gre mirror gt11
```

### ۶.۳. با پنل وب (GRE تنها)

1. ابتدا روی **سرور ایران**: **GRE Tunnels** → **New tunnel**.
2. IP عمومی همین سرور (ایران) و IP عمومی سرور خارج را وارد کنید.
3. IPهای خصوصی را خالی بگذارید تا پنل یک جفت `/30` آزاد پیشنهاد دهد
   (پیش‌فرض `10.100.111.1/30` و `10.100.111.2/30`). برای نقش ایران، سمت
   محلی باید `10.100.111.2/30` باشد.
4. ذخیره کنید؛ یونیت `gre-tunnel@gt11` ساخته و فعال می‌شود.
5. روی همان ردیف، **Mirror config** را بزنید، کپی کنید و روی سرور خارج در پنل
   (یا با CLI) همان را ذخیره کنید — local/remote خودکار جابه‌جا می‌شوند.

برای انجام یک‌مرحله‌ای GRE + FRP از ویزارد **Dashboard → FRP over GRE Reverse —
Quick Setup** استفاده کنید (بخش ۶.۱).

### ۶.۴. تست لینک

```sh
ip -br a show gt11                 # آیا اینترفیس UP است؟
ip tunnel show gt11                # local/remote درست است؟
ping -I gt11 10.100.111.2 -c3      # از سمت خارج به ایران
ping -I gt11 10.100.111.1 -c3      # از سمت ایران به خارج
frp-gre status gt11                # آمار rx/tx
frp-manager gre list               # وضعیت همه‌ی تانل‌ها + دسترسی به peer
```

در پنل هم دکمه‌ی **Link test** همین بررسی را انجام می‌دهد.

اگر `ping` جواب نداد، یعنی هنوز طرف مقابل پیکربندی نشده یا پروتکل ۴۷ در مسیر بسته است.

## ۷. پیکربندی FRP روی تانل

### ۷.۱. سرور (روی سرور ایران)

**CLI:** منو → **۲) Setup FRP Server**. پاسخ‌های پیشنهادی:

| پرسش | مقدار |
|---|---|
| `bindPort` | `7025` (یا `7000`) |
| پروتکل | `1) none` (TCP ساده — پیشنهادشده روی GRE) یا `2) quic` |
| TCP Mux | `n` |
| Bind address | گزینه **۳** و بعد `10.100.111.2` (IP تانل ایران) |
| Auth token | خالی بگذارید تا یک توکن تصادفی ۳۲ کاراکتری ساخته شود |
| metrics dashboard | `y` (پورت `7500`–`7599`، فقط روی `127.0.0.1`) |

**پنل:** **FRP Servers** → **New server** → در فیلد *Bind address* گزینه‌ی
`10.100.111.2` (IP تانل ایران) را انتخاب کنید. توکن ساخته می‌شود؛ یک‌بار نشان داده
می‌شود، کپی کنید.

> چرا `bindAddr` را IP تانل ایران می‌گذاریم؟ چون در این حالت `frps` فقط بسته‌هایی را
> می‌پذیرد که از داخل تانل می‌آیند و پورت کنترل روی اینترنت عمومی دیده نمی‌شود.

### ۷.۲. کلاینت (روی سرور خارج)

**CLI:** منو → **۳) Setup FRP Client**:

| پرسش | مقدار |
|---|---|
| Server IP | `10.100.111.2` (IP تانل ایران) |
| Server port | `7025` (همان پورت کنترل) |
| Auth token | همان توکن سرور (`g` = ساخت توکن جدید) |
| Transport | `1) tcp` (داخل تانل کافی است؛ باید با پروتکل سرور یکی باشد) |
| TCP Mux | `n` |
| Compression | `n` (فشار RAM می‌آورد) |
| TLS transport | `y` |
| per-proxy encryption | `y` |
| forward UDP too | `y` (برای هر پورت هم TCP و هم UDP) |
| ports | مثلاً `22,6000-6006` (پورت‌های محلی روی همین سرور خارج) |
| instance name | `client-7025` |

**پنل:** **FRP Clients** → **New client** → آدرس سرور `10.100.111.2`، توکن را پیست
کنید، پورت‌ها را وارد کنید و کلید **TCP+UDP** را روشن بگذارید.

TLS و رمزنگاری در پنل به‌صورت پیش‌فرض روشن‌اند. برای ترافیک داخلی
ازپیش‌رمزنگاری‌شده، گزینه‌ی **Raw speed** را روشن کنید تا TLS، رمزنگاری FRP،
compression و tcpMux خاموش شوند. ویرایش کلاینت هم لیست پورت‌ها را به‌صورت
کاما‌دار جایگزین می‌کند و کلیدهای ناشناخته‌ی TOML را حفظ می‌کند.

### ۷.۳. تست نهایی

```sh
# روی سرور ایران (frps پورت سرویس را روی خودش باز می‌کند)
ss -lntp | grep -E '7025|6000'
curl -I http://127.0.0.1:6000        # سرویسی که روی پورت ۶۰۰۰ سرور خارج است
```

از بیرون (کاربر):

```sh
curl -I http://1.2.3.4:6000
ssh -p 6000 user@1.2.3.4
```

روی سرور خارج، `frpc` باید فعال باشد و در لاگ خود اتصال به `10.100.111.2:7025`
را نشان دهد.

داشبورد پنل هم تأخیر (latency) مسیر عمومی و مسیر داخل تانل را زنده نشان می‌دهد.

## ۸. پنل وب

بخش‌های پنل:

- **Dashboard** — کارت سرویس‌ها (frps/frpc/GRE/پنل)، نمودار زنده‌ی تأخیر ICMP/TCP روی
  مسیر عمومی و مسیر تانل، تعداد اتصال و پهنای باند. دکمه‌ی
  **FRP over GRE Reverse — Quick Setup** هر دو نیمه‌ی تانل (GRE + frps/frpc + توکن +
  mirror payload) را در یک ویزارد می‌سازد.
- **FRP Servers** — ساخت/ویرایش/حذف سرور، تولید مجدد توکن، انتخاب `bindAddr`
  (`0.0.0.0`، `::`، IP تانل)، مشاهده‌ی خام TOML. در نقش ایران، `10.100.111.2` را
  انتخاب کنید.
- **FRP Clients** — ویزارد پورت‌ها با کلید TCP/TCP+UDP، توکن، آدرس سرور، ویرایش ساختاریافته با حفظ کلیدهای TOML ناشناخته.
  در نقش خارج، آدرس سرور `10.100.111.2` است.
- **GRE Tunnels** — ساخت/حذف، پیشنهاد خودکار `/30`، تست لینک، Mirror config.
- **Turbo / ZRAM** — اعمال BBR + fq + بافر ۳۲ مگ، فعال‌سازی ZRAM.
- **Logs** — لاگ زنده‌ی هر یونیت (`journalctl -f`)، فیلتر یونیت، توقف و پاک‌کردن.
- **Stats** — آمار FRP از `webServer` با تاریخچه‌ی ۲۴ ساعته.
- **Backup** — خروجی ZIP و ورودی با کشیدن‌ورهاکردن، با کلید «شامل توکن‌ها».
- **Watchdog** — روشن/خاموش و آستانه‌ها.

نکته‌های مهم:

- هر نوشتن کانفیگ اول با `frps verify` / `frpc verify` بررسی می‌شود، بعد از فایل قبلی
  نسخه‌ی `.bak-<تاریخ>` گرفته می‌شود و در نهایت فایل به‌صورت اتمیک جایگزین می‌شود.
- اگر کانفیگی دستی یا با قالب پیشرفته ساخته شده باشد، ویرایش ساختاری رد می‌شود (کد ۴۰۹)
  و باید از ویرایشگر raw استفاده کنید.
- پنل هرگز خودش را ری‌استارت نمی‌کند؛ اگر `panel.toml` را عوض کردید، خودتان سرویس را
  ری‌استارت کنید.

| `/root/frp/gre/*.env` | تعریف تانل‌ها (`LOCAL_PUBLIC_IP`، `REMOTE_PUBLIC_IP`، `IFACE`، …) |

| `/usr/local/bin/frps`، `frpc` | باینری‌های FRP |
| `/usr/local/bin/frp-panel` | پنل |
| `/usr/local/bin/frp-manager` | CLI |
| `/usr/local/bin/frp-gre` | helper تانل (از داخل باینری/CLI نصب می‌شود) |

یونیت‌ها:

```
frps@server-7025.service      ← سرور
frpc@client-7025.service      ← کلاینت
gre-tunnel@gt11.service       ← تانل
frp-panel.service             ← پنل

```

## ۱۱. بهینه‌سازی و پایداری

### Turbo

روی **هر دو** سرور:

```sh
frp-manager turbo apply      # BBR + fq + بافرهای ۳۲ مگ، به‌صورت پایدار
frp-manager turbo status
frp-manager turbo revert
```

در پنل: **Turbo / ZRAM** → Apply. (پنل مستقیم `sysctl` را دست نمی‌زند؛ یونیت
`frp-turbo` را نصب و از طریق systemd اجرا می‌کند.)

### ZRAM

```sh
frp-manager turbo zram-on --size 2048 --algo lz4
frp-manager turbo zram-status
```

### Watchdog

```sh
frp-manager watchdog enable --interval 15 --threshold 3 --cooldown 60
frp-manager watchdog status
```

واچ‌داگ دولایه‌ای است: **لایه ۱** هر تانل GRE را با ping از داخل اینترفیس بررسی می‌کند و پس از
سه شکست پیاپی `gre-tunnel@…` را بازسازی و همه‌ی `frpc@…`های فعال را ری‌استارت می‌کند.
**لایه ۲** وقتی GRE سالم است، اتصال کنترل `serverAddr:serverPort` و وضعیت proxyها را از
`webServer` لوکال (در صورت فعال بودن) بررسی می‌کند و فقط همان `frpc` گیرکرده را ری‌استارت
می‌کند. رخدادهای ساختاریافته (`action=… layer=… unit=… reason=… result=…`) در
`/var/log/frp-panel/watchdog.log` ثبت می‌شوند (در پنل: بخش Watchdog). پیش‌فرض‌ها:
`15s` / `3` / `60s`.

اعلان تلگرام اختیاری است: اگر `TG_BOT_TOKEN` و `TG_CHAT_ID` تنظیم شده باشند،
هر رخداد heal (لایه، یونیت، دلیل، تعداد شکست، نتیجه) به تلگرام ارسال می‌شود.
ارسال در یک subshell پس‌زمینه با `curl --max-time 5` انجام می‌شود و هرگز حلقه‌ی
واچ‌داگ را متوقف نمی‌کند. روی سرورهایی که تلگرام فیلتر است، `TG_API_BASE` را
به یک Cloudflare Worker پروکسی بدهید. توکن در پاسخ‌های API ماسک و در بکاپ
بدون secrets با `REDACTED` جایگزین می‌شود.

```sh
frp-manager watchdog telegram --token '123456:ABC…' --chat -1001234567890
frp-manager watchdog telegram --api-base https://tg.example.workers.dev
frp-manager watchdog test-telegram
```

## ۱۴. امنیت

- **توکن ۳۲ کاراکتری تصادفی** به‌صورت خودکار ساخته می‌شود (توکن پیش‌فرض ثابت وجود ندارد).
  اگر توکن لو رفت، از پنل **Regenerate** بزنید و کلاینت‌ها را به‌روز کنید.
- `frps` را روی **IP تانل ایران** (`10.100.111.2`) بایند کنید تا پورت کنترل روی
  اینترنت نباشد.
- پنل به‌صورت پیش‌فرض روی `0.0.0.0` بایند می‌شود و نصب‌کننده پورت را در `ufw` باز
  می‌کند. اگر دسترسی عمومی نمی‌خواهید، با `--bind 127.0.0.1` یا IP تانل نصب کنید و
  قاعده‌ی UFW را ببندید؛ پورت را در فایروال ارائه‌دهنده‌ی ابری هم بررسی کنید.
- فایروال: روی **ایران** پروتکل ۴۷ از IP خارج و پورت‌های سرویس را باز کنید؛ روی
  **خارج** فقط پروتکل ۴۷ از IP ایران لازم است (سرور خارج هیچ پورت سرویسی را روی
  اینترنت باز نمی‌کند).

نمونه (سرور ایران — ورودی، iptables):

```sh
iptables -A INPUT -p gre -s <IP-خارج> -j ACCEPT
iptables -A INPUT -p tcp -m multiport --dports 6000:6006 -j ACCEPT
iptables -A INPUT -p udp -m multiport --dports 6000:6006 -j ACCEPT
```

نمونه (سرور خارج — خروجی/بک‌اند، iptables):

```sh
iptables -A INPUT -p gre -s <IP-ایران> -j ACCEPT
```

با `ufw`:

```sh
# روی ایران (ورودی)
ufw allow from <IP-خارج> proto gre
ufw allow 6000:6006/tcp
ufw allow 6000:6006/udp

# روی خارج (خروجی/بک‌اند)
ufw allow from <IP-ایران> proto gre
```

> helper تانل، وقتی سیاست `FORWARD` روی `DROP` باشد، قواعد لازم برای عبور ترافیک تانل را
> خودش اضافه می‌کند؛ ولی `INPUT` مربوط به خود میزبان را باید خودتان باز کنید.

- بکاپ‌های حاوی توکن را رمزگذاری یا در جای امن نگه دارید.
- پنل: ورود با محدودیت نرخ (۵ تلاش در دقیقه به ازای هر IP) و قفل نمایی؛ نشست‌ها کوکی
  `HttpOnly` + `SameSite=Strict` با تمدید لغزان ۱۲ ساعته.

## ۱۵. پرسش‌های متداول

**آیا GRE امن است؟**
خود GRE رمزنگاری و احراز هویت ندارد. امنیت این معماری از FRP می‌آید: TLS روی ترانسپورت،
توکن ۳۲ کاراکتری و رمزنگاری per-proxy. اگر به رمزنگاری لایه‌ی تانل نیاز دارید، GRE
مناسب نیست و باید از WireGuard/IPsec استفاده کنید.

**اگر پروتکل ۴۷ در مسیر بسته باشد چه؟**
تانل GRE برقرار نمی‌شود. جایگزین: FRP را بدون GRE و با `transport = "quic"` یا
`"websocket"` روی TLS اجرا کنید (در ویزارد کلاینت قابل انتخاب است). در این حالت مزیت
«پنهان‌بودن پورت کنترل» را از دست می‌دهید، ولی سرویس کار می‌کند.

**آیا هر دو سرور به IP عمومی نیاز دارند؟**
برای GRE بله؛ هر دو طرف باید بسته‌های پروتکل ۴۷ را دریافت کنند.

**ویزارد «FRP over GRE Reverse» چه می‌کند؟**
هر دو نیمه‌ی معماری را یک‌جا می‌سازد: روی ایران `gt11` + `frps` بایندشده به
`10.100.111.2` + توکن ۳۲ کاراکتری + mirror payload؛ روی خارج `gt11` قرینه + `frpc`
با TLS/رمزنگاری + پورت‌های درخواستی + تست لینک (ping از داخل تانل و وضعیت یونیت).
در پنل: Dashboard → Quick Setup؛ در CLI: منو ۱۴ یا `frp-manager reverse …`.

**آیا می‌توانم چند سرور/کلاینت روی یک ماشین داشته باشم؟**
بله. هر نمونه با پورت/نام خودش یک فایل TOML و یک یونیت جدا دارد
(`frps@server-7025`، `frps@server-7001`، …).

**IP تانل را می‌توانم عوض کنم؟**
بله، در پنل هنگام ساخت تانل جفت `/30` دیگری بدهید (مثلاً `10.100.112.1/30` و
`10.100.112.2/30`). فقط باید هر دو طرف یکی باشند.

**پنل روی سرور ایران هم لازم است؟**
نه. پنل و CLI مستقل‌اند؛ می‌توانید فقط CLI نصب کنید. اگر هر دو طرف پنل داشته باشند،
مدیریت و مانیتورینگ هر دو نود از یک داشبورد ممکن است.

**چرا ویرایش یک کانفیگ در پنل با خطای ۴۰۹ رد می‌شود؟**
کانفیگ با قالب پیشرفته/دستی نوشته شده و پنل نمی‌خواهد ساختارش را خراب کند. از ویرایشگر
raw همان صفحه استفاده کنید.

**محدودیت‌های فعلی چیست؟**
رابط فقط انگلیسی است (i18n/RTL در نقشه راه نیست)، فدراسیون چندنودی وجود ندارد و
هر پنل فقط نود خودش را مدیریت می‌کند.
